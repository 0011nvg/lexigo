# LEXIGO — техническое задание этапа 5 (проект, без подключения сервера)

Статус: **архитектурное предложение, не реализовано**. Этап 4 — локальный демонстрационный прототип; localStorage не обеспечивает аутентификацию, защиту от подделки, обмен между устройствами и доказательство авторства учительского подтверждения.

## 1. Роли и маршруты

- **Учитель**: подтверждённая учётная запись, управление только своими классами, назначение классу или конкретным зачисленным ученикам, просмотр агрегированной и персональной аналитики, подтверждение просмотра конкретной попытки.
- **Ученик**: собственная учётная запись/безопасный вход по приглашению, доступ только к своим назначениям, попыткам и словарному прогрессу.
- **Родитель**: отдельная учётная запись, доступ только к ребёнку после явного подтверждения связи школой/уполномоченным учителем; отсутствие автоматического доступа по коду класса или совпадению фамилии.
- **Администратор организации** (если нужен): управление приглашениями и принадлежностью педагогов к организации; без доступа к детским результатам сверх установленной необходимости.

Код класса — **приглашение**, не пароль и не доказательство личности; не должен раскрывать список учеников. Вход и восстановление доступа с ограничением попыток, истечением срока приглашения и отзывом токенов. Для взрослых — email с подтверждением; сценарий несовершеннолетних согласовать с требованиями школы и применимым правом до запуска.

## 2. Модель Supabase (предлагаемая)

- `organizations(id, name)`; `profiles(user_id PK references auth.users, display_name, role, organization_id, created_at)`.
- `classes(id, organization_id, teacher_user_id, grade, title)`; `enrollments(id, class_id, pupil_user_id, status)`, уникальная пара класс/ученик.
- `parent_pupils(parent_user_id, pupil_user_id, verified_by, verified_at, revoked_at)`; связи создаёт только уполномоченный педагог/администратор.
- `vocabulary_sections(id, grade, module, title, order_index)`; `vocabulary_words(id, section_id, en, ru, order_index)`; исходный словарь **1035 записей** импортируется без редактирования и с контрольной суммой.
- `assignments(id, class_id, created_by, section_id, mode, due_at, audience_type, created_at)`; `assignment_recipients(assignment_id, pupil_user_id)` для индивидуальных назначений. При `audience_type=class` доступ вычисляется по актуальному зачислению; индивидуальный — по recipient + enrollment.
- `attempts(id, assignment_id, pupil_user_id, started_at, finished_at, mode, status, first_answer_count, first_correct_count, client_session_id)`; `attempt_events(id, attempt_id, word_id, event_index, event_type, correct, hinted, retry, created_at)`. Различать самооценку карточек и проверяемые ответы; первая точность = правильные без подсказок / все первые проверяемые ответы.
- `teacher_reviews(id, attempt_id, teacher_user_id, reviewed_at, revoked_at)`; это отметка **просмотра учителем**, не независимая экзаменационная проверка и не утверждение правильности всех ответов.
- `audit_log` для административных изменений и отзывов связей; политика хранения и удаления определяется до пилота.

## 3. Авторизация и RLS: обязательные инварианты

Включить RLS на **каждой** таблице с персональными данными, default deny. Никогда не принимать `pupil_user_id` из URL или тела запроса как источник прав: сервер сопоставляет его с `auth.uid()`. Проверять связи по ключам и RLS на сервере, не только фильтрацией JavaScript.

| Действие | Ученик | Учитель | Родитель |
| --- | --- | --- | --- |
| Чтение назначения | Только своё (класс/recipient) | Только собственный класс | Только подтверждённо связанный ребёнок |
| Создание попытки | Только за себя и своё задание | Нет от имени ученика | Нет |
| Просмотр попыток | Только свои | Только учеников своих классов | Только связанного ребёнка |
| Подтверждение просмотра | Нет | Только свои классы, с идентификатором учителя | Нет |
| Изменение связей | Нет | По разрешённому сценарию приглашения | Только запрос, не самоподтверждение |

Критические операции (создание приглашений, подтверждение родства, учительские отзывы, экспорт персональных данных) — через серверные RPC/Edge Functions с проверкой прав и журналированием. **Service role key никогда не передавать в браузер**. Публичный anon key допустим только при корректном RLS.

## 4. Надёжность событий и аналитика

Попытки — append-only после завершения; ограничить частоту, размер и типы событий; idempotency key для повторной отправки; серверная проверка существования слова в назначенном разделе, режима и индекса события. События клиента остаются свидетельством взаимодействия, а не защищённым экзаменационным результатом. Валидация UTC-времени на сервере; хранить часовой пояс пользователя отдельно для отчётов.

Считать точность первой попытки на сервере по каноническому правилу, исключая карточки-самооценку, повторы и подсказки из числителя. Для трудных слов учитывать реальные ошибки и подсказки; отчёт обязан указывать количество наблюдений и не создавать оценку при нулевой выборке. Избегать двойного подсчёта при перезагрузке/повторной синхронизации.

## 5. Приватность и миграция

Демо-данные **не загружать автоматически**. Предусмотреть явный отказ/согласие и импорт только проверяемых записей, после аутентификации и сопоставления локального профиля с подтверждённой серверной учётной записью. Без достоверной привязки — не переносить. Экспорт CSV с техническими ID — псевдонимизация, не гарантия анонимности.

Определить минимизацию собираемых данных, сроки хранения, удаление по запросу, резервные копии, процедуру инцидента, контроль доступов, законные основания обработки сведений несовершеннолетних и подходящий регион размещения. До согласования этих вопросов **не подключать реальных детей**.

## 6. Приёмочные тесты этапа 5

1. RLS: ученик A не читает/не изменяет задания, события и профиль B (в том числе одноклассника); прямые REST/RPC-запросы возвращают отказ.
2. Родитель A не видит ребёнка B; отозванная связь блокирует доступ немедленно.
3. Учитель A не видит класс учителя B и не может подтвердить его попытку.
4. Классное назначение видно каждому зачисленному, индивидуальное — только адресату; проверка в интерфейсе **и** через API.
5. Повторная отправка события не удваивает аналитику; ошибки, подсказки и самооценки считаются корректно.
6. Выход из аккаунта очищает чувствительные локальные кеши; на общем устройстве данные предыдущего пользователя не показываются.
7. Мобильные экраны 320/390/768 px, клавиатура, focus-visible, screen reader, масштаб 200%, медленная сеть и offline/error states.
8. Проверка словаря: 236 + 423 + 376 = **1035**, неизменные ID/порядок/переводы, все существующие игровые режимы работают.
9. Проверить отзыв приглашения, просроченный токен, подмену pupil ID, CSRF/XSS, rate limits, пагинацию и аудит логов.

## 7. Рекомендуемая последовательность реализации

Сначала проект схемы и миграций в отдельной ветке без production-ключей → RLS и негативные интеграционные тесты → безопасные приглашения и вход → привязка учеников/родителей → запись попыток и агрегаты → проверка на тестовых фиктивных аккаунтах → согласование приватности → ограниченный пилот. Каждая фаза имеет отдельный PR и откат.
