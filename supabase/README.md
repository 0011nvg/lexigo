# Этап 5 — безопасная серверная основа (черновик PR)

**Не развёрнуто.** Эти файлы не подключают Supabase к сайту, не создают реальные аккаунты и не меняют игры или словарь. Техническое задание: [docs/stage-5-technical-spec.md](../../docs/stage-5-technical-spec.md).

## Состав
- `migrations/202610210001_stage5_foundation.sql`: таблицы, ограничения, минимальные права, RLS и функции проверки доступа.
- `migrations/202610210002_privileged_operations.sql`: выдача и отзыв приглашений, подтверждение/отзыв связи родителя, учительская отметка просмотра; все операции доступны **только service_role**.
- `migrations/202610210003_access_revocation.sql`: отзыв зачисления ученика и отметки просмотра учителем. При отзыве зачисления аннулируются все ещё не использованные ученические приглашения в класс (они являются общими токенами класса).
- `tests/rls_isolation.sql`: транзакционный тест отрицательных сценариев на *одноразовой локальной базе*. Использует фиктивные UUID и адреса `.invalid`, завершает `ROLLBACK`.
- `../tests/stage5-security.mjs`: статические инварианты для CI, **не замена PostgreSQL-тестам**.

## Как запускать после установки локального Supabase
1. Подготовить отдельную одноразовую локальную БД Supabase с актуальными `auth.users`, ролями `authenticated`/`service_role` и схемой `auth`. **Не запускать на рабочей базе.**
2. Применить все три миграции по порядку, с учётной записью владельца миграций.
3. Запустить `psql -v ON_ERROR_STOP=1 -f supabase/tests/rls_isolation.sql` от роли, которая может создавать фиктивных `auth.users` и переключаться на `authenticated`. Тест завершает транзакцию откатом.
4. Для автоматической проверки используйте `.github/workflows/stage5-postgres.yml`: PostgreSQL 16 в одноразовом контейнере, минимальный тестовый `auth`-stub, все три миграции и оба SQL-набора негативных сценариев.
5. Выполнить отдельный набор API/RPC и конкурентных тестов, проверить владельцев `SECURITY DEFINER` и grants, до любого развёртывания.

**Ограничения:** GitHub Actions запускает SQL на настоящем PostgreSQL 16 с **минимальной имитацией Supabase Auth**, но не проверяет полноценный Supabase Auth, PostgREST, JWT, Edge Functions или гонки конкурентных транзакций. Статический Node.js-тест также не доказывает безопасность. Перед merge/deploy нужны полноценные Supabase-тесты и независимый аудит RLS.

## Доверенная граница
`service_role` хранится исключительно в серверной Edge Function, никогда в HTML, JS, GitHub Actions logs или localStorage. Сервер **сам** проверяет JWT, получает идентификатор пользователя и передаёт его в привилегированные функции; значения actor/user из клиентского запроса не считаются подтверждёнными. Вход ребёнка и подтверждение родства требуют отдельного согласованного процесса. Код приглашения одноразовый, хранится как SHA-256, имеет срок действия и может быть отозван; приглашение родителя **не создаёт автоматически связь с ребёнком**.

При следующей итерации необходимо добавить миграции и серверные проверки для атомарного назначения конкретному ученику, безопасной записи событий с лимитами и идемпотентностью, а также очистки данных при выходе. Защита от записи событий в завершённую попытку уже проверяется SQL-тестом, но проверки конкурентных транзакций и неизменяемости остальных полей требуют расширения.


## Итерация: локальный JWT-контракт и проект Edge API

- `local-api/jwt-gateway.mjs` и `tests/stage5-jwt.mjs`: криптографическая проверка **локальных фиктивных HS256 JWT**, истечения срока, подписи и отказа при подмене actor/pupil ID. Это настоящая HMAC-подпись, но **не** JWT, выданный Supabase Auth.
- `functions/learning-api/index.ts`: **неразвёрнутый** проект Edge Function. Получает пользователя через `supabase.auth.getUser(accessToken)`, затем передаёт `user.id` в серверные RPC. Клиентские actor/pupil ID отклоняются. Service-role берётся только из серверного окружения.
- `migrations/202610210004_atomic_api.sql` и `tests/atomic_api.sql`: атомарное назначение адресатам, идемпотентное создание попытки и событий с `FOR UPDATE`, завершение попытки и отрицательные SQL-тесты. Проверяются в PostgreSQL CI.

**Ограничение:** Edge Function ещё не запускалась в настоящем локальном Supabase Runtime. Для её работы потребуется безопасно настроить PostgREST exposure схемы `lexigo` только для необходимых RPC, убедиться в grants и добавить интеграционные HTTP-тесты с JWT, выпущенными локальным Supabase Auth. Прямой доступ к `service_role` с клиента запрещён. Пока PR остаётся draft; production не подключать.


## Реальный локальный Supabase E2E (следующая проверка)

`.github/workflows/stage5-supabase.yml` поднимает изолированные сервисы Supabase CLI: Auth, PostgREST, PostgreSQL и отдельно Edge Function. Ключи берутся только из `supabase status -o env` внутри CI; никаких production-секретов в репозитории нет. `tests/stage5-supabase-e2e.mjs` создаёт исключительно фиктивные аккаунты `@example.invalid`, получает JWT через Auth signup, обращается к Edge HTTP, проверяет разграничение доступа через PostgREST, идемпотентность игровых событий и отзыв связи родителя.

Тестовая функция запущена с `--no-verify-jwt` **только внутри изолированного CI**: функция самостоятельно вызывает `auth.getUser(token)` и отказывает в доступе при неподтверждённом JWT. При production-развёртывании необходимо отдельно проверить gateway JWT enforcement и политику сетевого доступа. 

**Критерий завершения:** workflow должен завершиться SUCCESS; одно лишь наличие тестового кода не подтверждает работоспособность полного стека. Прямые RLS-политики старой схемы всё ещё разрешают некоторым authenticated-ролям записывать попытки и события без Edge Function; перед реальным развёртыванием нужно убрать этот обход и адаптировать SQL-тесты. Поскольку игровые ответы передаются клиентом, сервер пока не доказывает их правильность независимо.
