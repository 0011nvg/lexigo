# LEXIGO — аудит этапа 5, итерация PostgreSQL RLS

Дата: 21.10.2026. Область: черновой PR №2, **без развёртывания**.

## Угрозы и границы доверия

Атакующий может быть учеником, родителем или учителем, отправляющим запросы с собственным JWT, подставляющим чужие UUID и повторяющим запросы. Браузерные проверки и localStorage не являются защитой. PostgreSQL RLS должен изолировать строки, а привилегированные операции выполняются только через доверенную серверную функцию с независимо проверенной личностью пользователя.

## Проверки в GitHub Actions

`.github/workflows/stage5-postgres.yml` поднимает **настоящий PostgreSQL 16** в одноразовом контейнере, создаёт минимальный тестовый `auth.uid()` и фиктивных пользователей, применяет миграции, затем исполняет:

- `rls_isolation.sql`: чужие профили/классы/назначения/попытки/события, родитель после отзыва связи, попытка подмены pupil ID, ученик того же класса без права на индивидуальное задание, запись после завершения, повторный session ID, анонимный доступ.
- `privileged_operations.sql`: выпуск токена чужим учителем, однократность, срок действия, отзыв приглашения, соответствие роли, подтверждение/отзыв родительской связи, подтверждение завершённой попытки учителем и его отзыв, отзыв зачисления, отсутствие прямых прав на привилегированные функции.

Все SQL-тесты выполняются в транзакции с `ROLLBACK`, без настоящих детей и без production-ключей. Дополнительно CI запускает браузерные сценарии существующих игр и статический контроль словаря **236 + 423 + 376 = 1035**.

## Исправленные проблемы

1. **Неверная сигнатура GRANT:** первая попытка применения миграции на PostgreSQL обнаружила `revoke_parent_link(uuid,uuid)` вместо `revoke_parent_link(uuid,uuid,uuid)`. Исправлено, добавлена исполняемая проверка миграций.
2. **Неоднозначный отзыв доступа:** отзыв использованного приглашения не отменяет зачисление. Добавлена отдельная операция `revoke_enrollment` и аннулирование всех неиспользованных ученических приглашений класса. Родительская связь и учительская отметка просмотра отзываются независимо.
3. **Разделение организаций:** при погашении приглашения и подтверждении родительской связи проверяется организация пользователя.
4. **Прямой обход ролей:** таблицы приглашений и журнала не доступны клиентским ролям; учительские отметки нельзя вставить от имени ученика напрямую. Тестируются отказ чужому учителю и отказ неавторизованному пользователю.
5. **Завершённые попытки:** RLS не разрешает добавлять новые события в завершённую попытку; уникальный `client_session_id` препятствует повторному созданию одной и той же сессии для ученика.

## Оставшиеся риски — блокируют production

- Тестовый `auth`-stub **не равен** реальным Supabase Auth, PostgREST и JWT. Нужны отдельные тесты с подлинными локальными JWT и Edge Functions.
- Функции `SECURITY DEFINER` принимают actor UUID от **доверенного сервера**. Без проверки JWT на сервере вызывающий мог бы подставить чужой actor. Нельзя публиковать service_role ключ или открывать эти функции клиентам.
- Вспомогательные RLS-функции с UUID-параметрами доступны роли `authenticated` для работы политик. Их возможность раскрывать булевы сведения о чужих UUID требует отдельного privacy review и, возможно, переработки интерфейса.
- Нет проверенной атомарной серверной записи события/попытки, лимитов запросов, идемпотентности отдельных событий при конкурентных запросах и защиты от подделки игровых ответов на клиенте.
- Не реализованы пользовательский интерфейс входа, выпуск/отзыв JWT, полноценная проверка родства и безопасная миграция локальных данных. Настоящих учеников подключать нельзя.
- Перед применением миграций необходимы проверка конфигурации Supabase, согласование обработки персональных данных детей, сроки хранения, резервное копирование и независимый аудит RLS.
